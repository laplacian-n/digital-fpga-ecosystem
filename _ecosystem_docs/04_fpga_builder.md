# FPGA Builder — Technical Reference

Source studied: `FPGA_Builder_Package/source/fpga_builder.py` (2126 lines, single file,
`# -*- coding: utf-8 -*-`). Packaged as `FPGA_Builder.exe` via PyInstaller. UI strings
Thai, identifiers English. Companion files: `fpga_builder.json` (persisted config),
`อ่านก่อนใช้งาน.txt` (Thai install/usage manual), `examples/or_gate_example.vhd`

## 1. Overall architecture

**GUI framework:** pure `tkinter` / `ttk` (stdlib only — no PySide/Qt/wx). Imports at
`fpga_builder.py:29-30`:

```python
import tkinter as tk
from tkinter import ttk, filedialog, messagebox, scrolledtext
```

**Single class, single window.** The entire app is one class, `FPGABuilder(tk.Tk)`
(`fpga_builder.py:439`), instantiated and run at module scope:

```python
if __name__ == "__main__":        # 2124-2126
    app = FPGABuilder()
    app.mainloop()
```

There is no separation between "model" and "view" — widget state (`tk.StringVar`,
`ttk.Treeview` rows) *is* the app state. This is the central fact that drives the
headless-extraction recommendation in §7.

**Window/tab structure** (`_build_ui`, `fpga_builder.py:480-533`): a `ttk.Notebook`
with 3 tabs, plus a persistent bottom action bar and log pane that are packed
*before* the notebook (so they never get squeezed off small/scaled screens — see the
comment at `fpga_builder.py:481-484`):

- **Tab 1 "โปรเจกต์ & ชิป" (Project & chip)** — `_build_tab_project` (`:535-609`):
  ISE/Vivado tool paths, VHDL file list, board selector, part/speed/package/top
  entity fields, openFPGALoader path + cable selector.
- **Tab 2 "กำหนด Pin" (Pin assignment)** — `_build_tab_pins` (`:611-641`): clock
  period/name fields + a `ttk.Treeview` table (columns: signal, loc, io, extra) that
  is the pin map editor.
- **Tab 3 "ดูข้อมูล .bit" (.bit info viewer)** — `_build_tab_bit` (`:643-650`): opens
  a `.bit` file and shows its parsed header.
- **Bottom bar** (`:501-521`): `▶ Build .bit`, `⬇ Program`, `■ หยุด` (stop),
  `💾 บันทึก .bit` (save-as), `ล้าง Log` (clear log), status label.
- **Log pane** (`:525-529`): a `scrolledtext.ScrolledText` fed by a
  `queue.Queue` (`self.log_queue`) drained every 120 ms by `_drain_log`
  (`:1772-1808`) running on the Tk main thread — this is the GUI's only
  thread-safety mechanism; all subprocess work happens on background
  `threading.Thread`s that only ever `put()` onto that queue.

**App lifecycle:**
1. `__init__` (`:440-477`) sizes/positions the window relative to screen resolution,
   initializes state (`self.vhdl_files`, `self.log_queue`, `self.proc`,
   `self.board_key = "apex"`, editor-related fields), calls `_build_ui()`, then
   `_load_config()`, then schedules `_drain_log` via `self.after(100, ...)`.
2. A one-time warning (`:467-477`) fires via `self.after(600, ...)` if `PROJECT_DIR`
   contains a space — Vivado cannot build under a path with spaces.
3. `mainloop()` runs; all build/program actions are triggered by button callbacks
   which spawn worker threads; results flow back through `log_queue`.
4. `destroy()` (`:2106-2121`) saves config and, if a Vivado build was mid-flight via
   Task Scheduler, force-kills it and deletes the scheduled task so nothing orphans
   after the GUI closes.

logic — important for §7):

The on-disk sample (`fpga_builder.json`) currently has `"board": "apex"`,
`"part": "xc6slx9"`, `"pkg": "tqg144"`, `"speed": "-2"` — i.e. configured for the
Spartan-6 board, `vhdl: []`, `pins: []` (fresh/default state).

### Where board/part/package are actually chosen

`BOARDS` dict (`:141-156`) is the single source of truth tying a board label to its
chip triple + clock defaults + toolchain:

```python
BOARDS = {
    "apex": {"label": "...", "part": "xc6slx9", "speed": "-2", "pkg": "tqg144",
             "pins": _PIN_DESC_APEX, "clk": "OSC", "period": "50", "tool": "ise"},
    "edge": {"label": "...", "part": "xc7s15", "speed": "-1", "pkg": "ftgb196",
             "pins": _PIN_DESC_EDGE, "clk": "clk", "period": "20", "tool": "vivado"},
}
```

Selecting a board in the Tab-1 combobox calls `_on_board_change` → `apply_board(key)`
(`:719-750`), which overwrites `var_part`/`var_speed`/`var_pkg`/`var_clkname`/
`var_period` from the `BOARDS[key]` dict and clears any pin/LOC values already
entered (different boards use incompatible pin-naming schemes — see §4). The
individual `Part`/`Speed`/`Package` comboboxes (`:577-585`) are still free-editable
after that, so a user *can* deviate from the board preset.

### To retarget the EDGE Spartan-7 XC7S15

The `"edge"` entry in `BOARDS` (`:149-155`) is **already configured** for exactly
this target:

```python
"edge": {
    "label": "EDGE Spartan-7 (XC7S15) - build ด้วย Vivado",
    "part": "xc7s15", "speed": "-1", "pkg": "ftgb196",
    "pins": _PIN_DESC_EDGE,
    "clk": "clk", "period": "20",       # OSC 50MHz = 20ns
    "tool": "vivado",
},
```

So, concretely: **part = `xc7s15`, package = `ftgb196`, speed grade = `-1`,
toolchain = Vivado** (`tool: "vivado"` routes `on_build()` into the Vivado branch,
§5). Full device string assembled at `:981`: `f"{part}{pkg}{speed}"` →
`xc7s15ftgb196-1`. Nothing needs to change in the code to target this chip — a user
just needs to pick "EDGE Spartan-7 (XC7S15)" in the board dropdown (or set
`"board": "edge"` in `fpga_builder.json`), which cascades part/pkg/speed/pins/clock
automatically via `apply_board()`. The only thing NOT automatic: the pin table
itself (Tab 2) must be re-populated for the new pin names (P123-style Spartan-6
locations are meaningless on the 7-series grid package), which `apply_board()`
already forces by clearing stale LOC values on board switch (`:735-743`).

## 3. VHDL port parsing

Two layers, both pure regex (no real VHDL parser/AST):

**`_ports_from_body(body)`** (`:245-271`) — given the text between an entity's
`is` and its `end`, finds the `port ( ... );` block:

```python
pm = re.search(r"port\s*\((.*)\)\s*;", body, re.IGNORECASE | re.DOTALL)
```

then splits on `;` into individual declarations, matches each against:

```python
mm = re.match(r"([\w\s,]+):\s*(in|out|inout)\s+(.*)", line, re.IGNORECASE | re.DOTALL)
```

Names are comma-split (`led, sw : in ...` style groups). If the type contains a
`downto` range (`re.search(r"\(\s*(\d+)\s+downto\s+(\d+)\s*\)", typ, ...)`), the bus
is **expanded into individual bit signals**: `led(3 downto 0)` → `led[0]`, `led[1]`,
`led[2]`, `led[3]`. Non-vector ports are kept as-is. Result: a flat `list[str]` of
signal names (bits of a bus appear as separate entries), which is exactly the
row-per-signal shape the pin-assignment `Treeview` wants.

**`analyze_vhdl(files)`** (`:292-326`) — the higher-level, multi-file entry point
used by both "auto-detect on add file" (`_add_vhdl`, `:672-678`) and the "ดึงขาจาก
VHDL" (import ports) button (`_import_ports`, `:762-799`):

1. Concatenates and comment-strips all given files via `_read_all` (`:274-282`,
   also strips `--...` comments with `re.sub(r"--.*", "", text)`).
2. Finds every `entity NAME is ... end` block with
   `re.finditer(r"\bentity\s+(\w+)\s+is\b(.*?)\bend\b", ...)`, building
   `entities = {lowername: (real_name, ports)}` and an `order` list preserving file
   order.
3. Determines which entities are **used as sub-components** (i.e. not top) by
   scanning for three instantiation idioms:
   - `component NAME` (component declaration)
   - `label : entity work.NAME` (direct entity instantiation)
   - `label : NAME port map` (component instantiation)
4. `top = ` the last-defined entity that is *not* in the "used" set (or, if all are
   used — unusual — the last entity in the file). This matches the pattern seen in
   `examples/or_gate_example.vhd`, where `sch_1` instantiates `sch_2` as a
   component, so `sch_1` (defined second, uses `sch_2`) is correctly picked as top.
5. Clock-name heuristic (`:317-325`): tries a fixed list of common names (`clk`,
   `clock`, `osc`, `ck`, `clkin`, `clk_in`, `mclk`, `sysclk`, `clk50`, `clk_50`,
   `clk100`, `gclk`) against the top's port base names (after stripping a `[n]` bus
   suffix), falling back to any port containing `"clk"` or `"clock"` as a substring.

Returns `(top_name, clk_or_None, top_ports_list)`.

**Data structure exposed to the GUI:** a flat `list[str]` of port/bit names. The pin
table (`ttk.Treeview`, columns `signal, loc, io, extra`) is populated 1 row per
name; `_import_ports` (`:762-799`) merges this against the *existing* table so
previously-set LOC/IOSTANDARD/extra values are preserved for signals that still
exist, and stale rows (signals removed from the VHDL) are dropped — this
merge-by-name behavior would need to be preserved (or explicitly decided against)
in a headless port.

There is no type/width validation beyond bus-range extraction — no rejection of
malformed VHDL, generics, or records; this is a "best-effort scraper," not a
compiler front end.

## 4. Board definitions & pin maps

Two board-pin dictionaries map **package pin/ball name → human label**:

- `_PIN_DESC_APEX` (`:53-83`) — Apex Surveyor-6 (Spartan-6 XC6SLX9, `tqg144`
  package). Keys are ISE-style pin numbers like `"P66"`, values are function labels
  (`"SW0"`, `"L0"`, `"MN0"` for 3-state logic monitor LEDs, 7-seg segments,
  DIP/expansion headers K1-K5, flash PROM pins, OSC/UART/buzzer).
- `_PIN_DESC_EDGE` (`:86-131`) — EDGE Spartan-7 (XC7S15, `ftgb196` package). Keys
  are 7-series ball-grid names like `"H11"`, `"K12"`. Covers: 50 MHz OSC (`H11`), 16
  slide switches, 5 push buttons, 16 LEDs (shared with LCD data / 7-seg pins —
  documented inline as needing a jumper, `:99-100`), 4 digit-enable lines, LCD
  control, buzzer/UART/WiFi/BT headers, audio, PS2, SPI ADC/DAC, 12-bit VGA, and a
  J5/camera (OV7670) expansion header — explicitly flagged in a comment (`:124-126`)
  as **not** matching the Spartan-6 manual's J5 pinout (chip-specific override).

**Sort key:** `_pin_sort_key(p)` (`:134-137`) handles both naming schemes with one
regex, `r"([A-Z]+)(\d+)$"`, returning `(letters, number)` so `"P123"` sorts as
`("P", 123)` and `"K12"` as `("K", 12)`.

**Dropdown generation:** `make_pin_list(desc)` (`:176-178`) builds strings like
`"K12  (LED D2/LCD_D7)"` sorted via `_pin_sort_key`; these populate the `loc` column
combobox in `_edit_cell` (`:836-838`, `vals = make_pin_list(self.board["pins"])`).
`pin_only(val)` (`:181-184`) reverses this — regex `r"\s*([A-Z]{1,2}\d{1,3})\b"` —
to recover the bare pin name when writing constraint files.

**IOSTANDARD:** a flat constant list `IOSTANDARDS` (`:46-47`) —
`["LVCMOS33", "LVCMOS25", "LVCMOS18", "LVCMOS15", "LVTTL", "LVDS_25", "SSTL18_II",
"PCI33_3"]` — offered as a second dropdown per pin row (`:836-838`, `io` column).
**Default is always `LVCMOS33`** wherever a row is created without an explicit value
(`_add_pin_row` default `io="LVCMOS33"` at `:753`; `_import_ports` fallback
`io or "LVCMOS33"` at `:793`; XDC writer fallback `io or "LVCMOS33"` at `:963`).
This matches both boards' actual bank voltage (documented as "LVCMOS33 ทั้งหมด" in
the manual, `อ่านก่อนใช้งาน.txt:111`).

Per-pin extras (a free-text `extra` column, e.g. `PULLUP` or `DRIVE=8` for ISE-style
`.ucf`, or `PULLDOWN true` for Vivado `-dict` XDC syntax) are appended verbatim to
the generated constraint line — an escape hatch for constraints the GUI doesn't
model explicitly.

## 5. Build flow

### Vivado (Spartan-7 / XC7S15) — the flow the ecosystem cares about most

Two files are generated per build via `_write_vivado_files(bdir)` (`:951-1018`),
where `bdir = os.path.join(PROJECT_DIR, "build")` (`:1048`, created with
`os.makedirs(bdir, exist_ok=True)`).

**1. `<top>.xdc`** (constraints) — for every row in the pin table with both a
signal and a LOC set:

```python
d = f"PACKAGE_PIN {loc} IOSTANDARD {io}"
if extra: d += f" {extra}"
f.write("set_property -dict {{ {} }} [get_ports {{{}}}]\n".format(d, sig))
```

plus, only if the clock signal is present among constrained ports:

```python
f.write(f"create_clock -name sys_clk -period {per} [get_ports {{{clk}}}]\n")
```

and unconditionally two board-config lines to silence config-voltage DRC warnings:

```python
f.write("set_property CFGBVS VCCO [current_design]\n")
f.write("set_property CONFIG_VOLTAGE 3.3 [current_design]\n")
```

**2. `build.tcl`** (the Vivado batch script) — reproduced verbatim
(`:985-1017`):

```tcl
catch {config_webtalk -install off}
read_vhdl "<abs path to each .vhd, forward slashes>"
...
read_xdc "<top>.xdc"
synth_design -top <top> -part <part><pkg><speed> -directive RuntimeOptimized
catch {
  foreach bc [get_cells -quiet -hier -filter {REF_NAME =~ BUFG*}] {
    set n [get_nets -quiet -of_objects [get_pins -quiet $bc/I]]
    if {[llength $n]} { set_property CLOCK_DEDICATED_ROUTE FALSE $n }
  }
}
place_design -directive Quick
route_design -directive Quick
write_bitstream -force "<top>.bit"
```

Notes on this template:
- `config_webtalk -install off` disables Vivado's phone-home telemetry
  (`catch{}`-wrapped so an unrecognized command on other Vivado versions doesn't
  abort the script).
- `-directive RuntimeOptimized` on synth and `-directive Quick` on place/route are
  deliberate speed choices for small student designs (comment at `:992-995`
  documents a measured ~50s → ~42s improvement); no `opt_design` step is run at all.
- The `BUFG` loop is a **generic, netlist-driven** workaround (not name-guessing —
  the comment at `:1001-1008` explains an earlier name-guessing approach broke) that
  finds every clock buffer instance and disables `CLOCK_DEDICATED_ROUTE` on its
  input net, so a clock fed through a non-clock-capable pin (e.g. a push button used
  as a manual clock in a lab) doesn't hard-fail placement (`[Place 30-574]` /
  `[Place 30-99]`) — it degrades to a warning instead.
- The device string assembled for `synth_design -part` is
  `f"{self.var_part.get()}{self.var_pkg.get()}{self.var_speed.get()}"` (`:981`) →
  for EDGE Spartan-7 this is **`xc7s15ftgb196-1`**.

**Working directory:** `bdir` = `<PROJECT_DIR>/build` — all generated files
(`.xdc`, `build.tcl`, `_run.bat`/`_task_run.bat`, logs, `.bit`) land here, and it is
also the `cwd` passed to the subprocess.

**Invocation (`on_build`, Vivado branch, `:1051-1086`):**

```python
cmds = [f'call "{vivado}" -mode batch -source build.tcl -nojournal -log vivado_build.log']
```

i.e. `vivado.bat -mode batch -source build.tcl -nojournal -log vivado_build.log`,
run from `bdir`. Before this, the code hard-blocks (`messagebox.showerror`, returns
without building) if either the Vivado binary path or the build directory absolute
path contains a space (`:1061-1069`) — Vivado's internal Tcl splits paths on
whitespace and fails synthesis, so this is caught proactively rather than left to
fail deep in synth.

**Execution isolation — this is the trickiest part of the whole file.** Because the
app is a PyInstaller `.exe` bundling its own Tcl 8.6.15, and Vivado needs its own
Tcl 8.6.13, running Vivado as a direct child process causes a Tcl version-conflict
crash (comment `:1078-1080`, `:1463-1468`). The workaround, `_run_via_scheduler`
(`:1534-1645`), launches the build through the **Windows Task Scheduler** instead of
`subprocess.Popen` directly:

1. Kills any orphaned prior Vivado/task-runner processes and clears `.Xil` lock
   dirs (`_kill_sched_build`, `_clean_vivado_locks`).
2. Writes `_task_run.bat` (cd to `bdir`, call the real `_run.bat`) and a VBScript
   launcher `_task_hidden.vbs` that runs it with `WScript.Shell.Run(..., 0, True)` —
   window style 0 = hidden, `True` = wait for completion.
3. `schtasks /create` a one-shot task named `FPGA_Builder_VivadoBuild` whose action
   is `wscript.exe //B //Nologo "<vbs>"`, then patches its settings via PowerShell
   `Set-ScheduledTask` to allow running on battery (`AllowStartIfOnBatteries`,
   `DontStopIfGoingOnBatteries`) — otherwise a laptop on battery silently queues the
   task and the build appears to hang forever (documented pitfall in
   `อ่านก่อนใช้งาน.txt:79-81, 88-97`).
4. `schtasks /run` to fire it, then polls for completion in `_wait_build`
   (`:1647-1726`) by tailing `vivado_build.log` for the literal string
   `"write_bitstream completed successfully"` **and** confirming the `.bit` file's
   mtime is newer than before the run (belt-and-braces against a half-written file
   or a stale success string), with a 900s overall timeout and several sub-timeouts
   for "never started" detection.
5. `schtasks /delete` cleans up the task definition afterward regardless of outcome.

This scheduler indirection is a **PyInstaller/Tcl-embedding artifact, not an
inherent property of the build logic** — a plain `python fpga_builder.py` run (not
frozen) would not need it, and a headless script run via plain `python3` (not
bundled) would not need it either. It's an important thing to note for the headless
API (§7): don't carry this complexity forward unless the headless tool itself is
also going to be PyInstaller-frozen with a conflicting Tcl.

**Where the `.bit` lands:** `build/<top>.bit`, referenced via
`os.path.join(bdir, f"{top}.bit")` (`:1083`, `:1106`), picked up by `_after_build`
(`:1108-1111`) which updates the "view .bit info" tab.

### ISE (Spartan-6 / XC6SLX9) — briefer, for contrast

`_write_build_files(bdir)` (`:906-948`) generates three files, all written with
`encoding="mbcs"` (ANSI/local codepage) because ISE's own tools read project files
in the system codepage, not UTF-8 — a recurring theme for every generated file in
this app:

- **`<top>.prj`** — one `vhdl work "<relative-or-absolute path>"` line per source
  file (using `path_for_tool` to avoid ISE's "different drive" `relpath` failure).
- **`<top>.xst`** — XST run script: `-ifn <top>.prj -ifmt mixed -ofn <top>.ngc
  -ofmt NGC -p <part><speed>-<pkg> -top <top> -opt_mode Speed -opt_level 1
  -keep_hierarchy no -iobuf yes`.
- **`<top>.ucf`** — one `NET "<sig>" LOC = "<pin>" | IOSTANDARD = <io> | <extra>;`
  line per constrained signal, plus (if clock present)
  `NET "<clk>" TNM_NET = "<clk>";` and
  `TIMESPEC TS_<clk> = PERIOD "<clk>" <period> ns HIGH 50%;`.

Toolchain invocation (`on_build`, ISE branch, `:1088-1106`) is a literal five-stage
Xilinx ISE command line pipeline, run in `bdir` after `call "<settings64.bat>"`
sources the ISE environment:

```
set "XILINXD_LICENSE_FILE=<bundled Xilinx.lic>"
xst -intstyle ise -ifn "<top>.xst" -ofn "<top>.syr"
ngdbuild -intstyle ise -aul -dd _ngo -nt timestamp -uc "<top>.ucf" -p <dev> "<top>.ngc" "<top>.ngd"
map -intstyle ise -p <dev> -w -ol high -t 1 -xt 0 -r 4 -mt off -ir off -pr off -lc off -power off -o "<top>_map.ncd" "<top>.ngd" "<top>.pcf"
par -intstyle ise -w -ol high -mt off "<top>_map.ncd" "<top>.ncd" "<top>.pcf"
bitgen -intstyle ise -w -g Binary:no -g CRC:Enable -g StartupClk:Cclk "<top>.ncd" "<top>.bit" "<top>.pcf"
```

Unlike Vivado, ISE is run directly via `subprocess.Popen(["cmd", "/c", bat], ...)`
(no Task Scheduler indirection needed — no Tcl conflict) with stdout/stderr piped
and streamed line-by-line into `log_queue` (`:1474-1489`), also scanned live for USB
error substrings.

**Common runner infrastructure:** `_run_flow(cwd, cmds, ...)` (`:1423-1532`) is
shared by both toolchains — it writes a batch file (`_run.bat`) with
`if errorlevel 1 exit /b 1` after each command (so any stage failure aborts the
chain), runs it (either directly, or via `_run_via_scheduler` when
`isolate=True`), and on failure scans the captured output (or `vivado_build.log`
for the Vivado path) through `_build_error_hint()` (`:1733-1770`), which matches
against the `_ERROR_HINTS` table (`:332-433`) to surface a plain-Thai diagnosis
(e.g. "you mixed `std_logic_unsigned` with `numeric_std`", "unconstrained port",
"DRC UCIO-1: pin not assigned", "out of memory", "path has spaces") plus a
best-effort extraction of the offending source line number(s), filtering out
library file paths so only the student's own file/line is surfaces.

## 6. Program/download flow (openFPGALoader)

Entirely GUI-invoked from `on_program_ofl()` (`:1257-1339`), using an external
`openFPGALoader.exe` (bundled at `tools/openFPGALoader/openFPGALoader.exe`,
resolved by `_resolve_ofl()` at `:1227-1255` with several fallback search paths and
a friendly Thai error if genuinely missing).

**Pre-flight checks before programming** (all GUI-only sanity checks, not build
logic):
- Reads the `.bit` header via `parse_bit_header()` and compares its embedded part
  string against the currently selected board's part, warning (not blocking) on
  mismatch (`:1268-1286`) — prevents "loaded fine, chip stayed unconfigured"
  confusion when e.g. a Spartan-6 `.bit` is programmed onto the Spartan-7 board.
- Compares the constraint file's mtime against the `.bit`'s mtime for the *current
  project's own* build output only, warning if the `.bit` predates the last pin
  edit (stale-build detection, `:1287-1311`).

**Mode selection** — `_ask_flash_mode()` (`:1189-1225`) pops a modal dialog with two
choices, matching the course's terminology exactly:
- `"sram"` → **"Normal Rom (Fast — Temporary)"**
- `"flash"` → **"PROM Rom (Slow — Permanent)"**

**SRAM (Normal Rom) command** (`:1316-1320`):

```
"<openFPGALoader.exe>" -c <cable> -m "<bit>"
```

`-m` loads to volatile SRAM configuration memory; nothing survives power-cycling.

**SPI Flash (PROM Rom) command** (`:1321-1334`):

```
"<openFPGALoader.exe>" -c <cable> -f -B "<spiOverJtag_bridge.bit>" "<bit>"
```

`-f` = write to SPI flash (permanent); `-B` explicitly points to a **spiOverJtag
bridge bitstream** — `_find_spioverjtag(ofl)` (`:1174-1187`) resolves this as
`spiOverJtag_<part><pkg>.bit` (e.g. `spiOverJtag_xc7s15ftgb196.bit`), searched next
to the loader exe, in `tools/openFPGALoader/`, or in a `share/openFPGALoader/`
sibling — needed because the compiled-in default bridge path only works inside a
full MSYS2 install, not this bundled/frozen distribution (`:1322-1324` comment).

**Cable**: `-c <cable>` where `cable` is one of `OFL_CABLES` (`:198-199`) —
`ft2232, digilent, digilent_hs2, digilent_hs3, ft232, ft231X, ft4232, bus_blaster,
jlink, cmsisdap, dirtyJtag` — default `ft2232`, which both the Apex (Spartan-6) and
EDGE (Spartan-7) boards use per the manual (`อ่านก่อนใช้งาน.txt:61`, distinguishing
"Dual RS232-HS" for Spartan-6 vs. "Digilent USB Device" for Spartan-7, both
Interface 0).

Before running either command, the loader's own directory is prepended to `PATH`
(`:1337-1338`) because the MSYS2-built `openFPGALoader.exe` shells out to `cygpath`
when writing flash, and that helper is bundled alongside it.

**USB driver / Zadig handling.** openFPGALoader talks to the FT2232 chip's
"Interface 0" over libusb, which requires the **WinUSB** driver rather than the
stock FTDI VCP/D2XX driver. The app detects the failure mode
(`"usb_open"`, `"unable to open ftdi"`, `"jtag init failed"`, `"no cable found"`
substrings scanned live from subprocess output, `:1483-1487`) and offers two
remediation paths from `_driver_help()` (`:1817-1877`):
1. **Automatic** (`_driver_auto_install`, `:1879-2041`) — an elevated (UAC,
   `Start-Process powershell -Verb RunAs`) PowerShell script that: imports the
   bundled `.inf`/`.cat` driver's self-signed certificate into
   `TrustedPublisher`+`Root` machine stores (the step Zadig does implicitly that
   `pnputil` alone does not), runs `pnputil /add-driver ... /install`, calls the
   Win32 `UpdateDriverForPlugAndPlayDevices` API against hardware ID
   `USB\VID_0403&PID_6010&MI_00` (covers all FT2232-based boards), disables/
   re-enables the parent composite USB device to force the binding to take effect
   without a physical replug, then **verifies** via `Get-PnpDeviceProperty
   DEVPKEY_Device_Service` that Interface 0's service is actually `WinUSB` before
   reporting success.
2. **Manual Zadig** — launches the bundled `tools/zadig.exe` and shows step-by-step
   instructions (List All Devices → select "(Interface 0)" → WinUSB → Replace
   Driver).

The manual also documents that `setup.bat` (not part of this Python file; a
separate bundled script) installs this driver once at install time so students
normally never see this dialog.

## 7. Extension point recommendation — headless build+program API

### What is already GUI-free (reuse directly)

These module-level functions have **no Tkinter dependency** and can be imported
and called as-is from a headless script/service:

- `analyze_vhdl(files)` / `parse_vhdl_ports(path)` / `_ports_from_body` /
  `_read_all` — VHDL scraping.
- `parse_bit_header(path)` — post-build/pre-program `.bit` introspection.
- `path_for_tool`, `pin_only`, `make_pin_list`, `_pin_sort_key` — path/pin string
  utilities.
- `BOARDS`, `_PIN_DESC_APEX`, `_PIN_DESC_EDGE`, `PARTS`, `SPEEDS`, `PACKAGES`,
  `IOSTANDARDS`, `OFL_CABLES` — all static data.
- `find_vivado()` — toolchain discovery (though a headless service will more likely
  want an explicit config value than autodetection).
- `_ERROR_HINTS` + the *logic* of `_build_error_hint` (the function itself only
  needs the log text, not `self`) — genuinely useful to keep for a headless CLI's
  error reporting too.

### What is entangled with GUI state (needs extraction)

Everything that currently reads `self.var_*`/`self.tree`/`self.vhdl_files` and
writes to `self.log`/`messagebox`/`self.log_queue` needs its **parameters
inverted**: instead of pulling values off widgets, these functions should take
plain arguments and return values/raise exceptions instead of showing dialogs or
disabling buttons. Concretely, the functions that contain the *real* build/program
logic today are:

| Current method | Core logic to extract | GUI coupling to strip |
|---|---|---|
| `_write_vivado_files(bdir)` (`:951-1018`) | XDC + `build.tcl` templating (§5) | reads `self.var_top/part/pkg/speed/clkname/period`, `self.tree`, `self.vhdl_files` |
| `_write_build_files(bdir)` (`:906-948`) | `.prj`/`.xst`/`.ucf` templating (ISE) | same as above |
| `on_build()` (`:1020-1106`) | orchestration: validate pins → write files → assemble command list → run | `messagebox` validation dialogs, `self.board["tool"]` dispatch, `_save_config()` side effect |
| `_run_flow` / `_run_via_scheduler` / `_wait_build` (`:1423-1726`) | subprocess execution, Task-Scheduler isolation, completion detection | `self.log_queue`, `self._busy*` flags, UI button enable/disable |
| `on_program_ofl()` / `_ask_flash_mode()` / `_find_spioverjtag()` (`:1174-1339`) | programming command construction (SRAM vs PROM) | `messagebox` confirmations, modal dialog for mode choice, `self.var_*` reads |
| `_driver_auto_install` / `_driver_help` (`:1811-2041`) | WinUSB driver install (Windows-only, optional for a backend that already assumes drivers are provisioned once) | entirely UI dialogs; the PowerShell payload itself is reusable as a standalone maintenance script |

### Proposed headless signatures

```python
def build_bitstream(
    vhdl_paths: list[str],
    top: str,
    part: str,            # e.g. "xc7s15"
    pkg: str,              # e.g. "ftgb196"
    speed: str,            # e.g. "-1"
    pin_map: list[dict],   # [{"signal": "led[0]", "loc": "K12", "io": "LVCMOS33", "extra": ""}, ...]
    clk_name: str | None,
    clk_period_ns: str | None,
    out_dir: str,          # build working directory (must be an absolute, space-free path)
    toolchain: str,        # "vivado" | "ise" — or infer from part prefix (xc7/xc6)
    vivado_path: str | None = None,
    ise_settings_path: str | None = None,
    timeout_s: int = 900,
) -> str:                  # returns path to the produced .bit, raises BuildError on failure
    ...

def program(
    bit_path: str,
    mode: str,             # "sram" | "flash"
    cable: str,            # e.g. "ft2232"
    openfpgaloader_path: str,
    part: str | None = None,   # needed to resolve spiOverJtag_<part><pkg>.bit when mode="flash"
    pkg: str | None = None,
    spiOverJtag_path: str | None = None,
) -> None:                 # raises ProgramError with parsed stderr on failure
    ...
```

`build_bitstream` internally would: (1) validate every `pin_map` entry has a
non-empty `loc` (today's `on_build` missing-pin check, `:1030-1045`); (2) call the
Vivado- or ISE-specific file-writer (ported from `_write_vivado_files`/
`_write_build_files`, with `self.tree`/`self.var_*` reads replaced by the function
arguments); (3) invoke the toolchain — for Vivado, this can very likely **drop the
Task Scheduler indirection entirely** if the headless entry point is a plain
`python3`/venv process (not a PyInstaller executable carrying its own conflicting
Tcl runtime) — a direct `subprocess.run([vivado_bat, "-mode", "batch", "-source",
"build.tcl", "-nojournal", "-log", "vivado_build.log"], cwd=out_dir)` should work
without the Tcl-version crash that motivated `_run_via_scheduler`. This removes a
large amount of Windows-specific complexity (schtasks, VBScript hidden launcher,
orphan-process killing, lock cleanup) that exists *only* to route around the frozen
GUI's embedded Tcl — verify this assumption on the actual target runtime before
committing to dropping it, since it's the single riskiest simplification; (4) poll
for/confirm `write_bitstream completed successfully` + fresh `.bit` mtime exactly as
`_wait_build` does today, since that success criterion (not just process exit code)
is what actually distinguishes genuine success from a `cmd` wrapper reporting `rc=0`
after a crashed child; (5) on failure, run the log through `_build_error_hint`-style
matching and raise a structured `BuildError(message, hint, source_lines)` instead of
popping a `messagebox`.

`program()` is comparatively simple to extract — it is already almost pure command
construction; only the two `messagebox`-based confirmations (chip-mismatch warning,
stale-`.bit` warning) and the modal mode-picker need to become either explicit
function arguments (`mode` is already one) or return-value warnings the caller
decides how to surface (a web UI or AI orchestrator would want these as structured
warnings/errors, not blocking OS dialogs).

### Global/state dependencies that make headless use hard today

- **Everything lives on `self`.** Board/part/pkg/speed/clock/pin-table state is
  read from `tk.StringVar`s and a live `ttk.Treeview` — there is no plain dict/dataclass
  representing "the current project" independent of widgets. A headless API needs
  an explicit `ProjectConfig`/`BuildRequest` dataclass (mirroring the JSON schema in
  §2) that both the GUI and the new API can serialize to/from, so the GUI becomes
  one more caller of the same core rather than the only caller.
- **`PROJECT_DIR` is a module-level global** (`:37-40`) derived from
  `sys.executable`/`__file__`, and `build/` is hardcoded relative to it
  (`os.path.join(PROJECT_DIR, "build")`, `:1048`). A multi-tenant backend serving
  many concurrent build requests (as the ecosystem hub implies) needs `out_dir` to
  be a parameter, not a global — the proposed signature above already does this,
  but note the Vivado build script writes absolute VHDL paths and a relative XDC
  reference (`read_xdc "<top>.xdc"`, `:991`) assuming `cwd == bdir`; concurrent
  builds must each get their own directory (this already works today since a fresh
  `bdir` per call is trivial, but the *shared* Task-Scheduler task name
  `"FPGA_Builder_VivadoBuild"` (`:1539`) is **not** concurrency-safe and would need
  a unique name per job if that indirection is kept).
- **Thread + Tk-queue coupling for progress reporting.** `_run_flow`'s progress and
  completion reporting is wired to a `queue.Queue` drained by a Tk `after()` loop
  (`:1772-1808`); a headless service should instead expose a synchronous return
  value (or, for a long-running web API, a generator/callback/websocket event
  stream) — the underlying polling logic in `_wait_build` (tailing a log file for a
  marker string + checking file mtime) is directly reusable, just needs its
  `self.log_queue.put(...)` calls replaced with a caller-supplied callback or
  yielded events.
- **`self._busy` / `self._busy_gen` single-flight guard** (`:1428-1435`,
  `on_stop`) currently allows only one build/program operation at a time,
  GUI-wide. A backend serving multiple pipeline requests (spec → draw → sim → VHDL
  → board) will want per-job isolation instead of a single global busy flag —
  i.e. this should become a per-job lock/lease keyed by `out_dir` or a job ID, not
  instance-level state on a singleton GUI object.
- **`_save_config()` / `_load_config()` conflate "last GUI session's settings" with
  "this build's parameters."** A headless API should not implicitly read/write
  `fpga_builder.json` on every build; tool paths (`vivado`, `ise`, `ofl`) should be
  environment/config-injected once at service startup, while per-build parameters
  (part/pkg/speed/pins/top/clock) should be fully explicit function arguments as in
  the proposed signature, decoupling "board profile" (a template) from "this
  specific build request" (an instance of that template plus a pin map).
- **Windows-only assumptions throughout**: `cmd /c`, `.bat` files written in `mbcs`
  encoding, `taskkill`, `schtasks`, PowerShell driver installation, `CREATE_NO_WINDOW`.
  If the hub is meant to be cross-platform eventually, the batch-file/cmd layer
  should be replaced by direct `subprocess.run([vivado_bat_or_sh, ...])` argument
  lists (Vivado ships a `vivado` shell script on Linux); this is out of scope for
  now since the toolchains themselves (ISE 14.7, Vivado on Windows for this course)
  are Windows-bound, but worth flagging since "headless" and "hub" both suggest
  eventual server deployment off a student's Windows laptop.

**Bottom line recommendation:** don't try to strip Tkinter out of `fpga_builder.py`
in place. Instead, lift the already-almost-pure logic in
`_write_vivado_files`/`_write_build_files` (file templating) and the process-running
core of `_run_flow`/`_wait_build` (minus the Tk queue) into a new
`fpga_backend.py` module exposing `build_bitstream()`/`program()` as described
above, backed by a plain dataclass config; then make the existing
`FPGABuilder` GUI a *thin caller* of that module (reading its widgets into a
`BuildRequest`, calling the module in a thread, and rendering the returned
result/exception into `log_box`/`messagebox` as it does today). This keeps the
GUI working unmodified for current students while giving the new ecosystem hub a
clean, testable, GUI-free entry point — and it's a much smaller/safer change than
trying to decompose the 2100-line Tkinter class first.
